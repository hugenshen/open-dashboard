1. 是不是主流？DataEase 一体协议优缺点？我们能否演进？

流派特征和谁像
查询意图 / Semantic Layer 配置归配置；查询用瘦 Spec；权限进计划 Open Dashboard 更接近主流演进方向
视图一体 calcData ChartView ≈ 请求 ≈ 响应；Handler 内拼 SQL + 塑形 DataEase 及不少开源 BI
前端聚合 浏览器内 filter/aggregate 当前 hi-fi 原型（演示态，需换成 chartQuery）
DataEase 优点
  • 前端省事：改完轴/筛选直接 getData(clone(view))
  • Handler 内聚，一种图一种 SQL/塑形，短期迭代快
  • 与 AntV/S2 深度绑定，导出/阈值可挂同一 DTO
缺点
  • DTO 膨胀；配置与运行时耦合，契约难版本化
  • SQL/权限散落 Handler；数据集难被非图表复用
  • 跨端（嵌入/OpenAPI/批量导出）都要背整份视图
Open Dashboard 优点
  • 契约清晰：保存配置 ≠ 取数请求
  • DatasetQuery 可复用（图/导出/嵌入/未来指标）
  • FilterAST + 限流/审计集中；换引擎不改存储
代价
  • 多一层编译（encode → QuerySpec）
  • 塑形适配器要显式维护
  • 短期不如「一把梭 getData」写得快
演进路径（不必推翻协议）： encode → QuerySpec → ResultTable → view(shape) → 指标口径层 / QuerySpec 指纹缓存 / 多端 shape。 复杂图暂时难编译时，允许调试态 inline QuerySpec，但禁止回退成整份 ChartView 当请求体。

2. 为什么开源 BI 爱用 DataEase 那套，我们却要拆开？

2.0 先用餐厅比喻（不用术语）

DataEase 像「整桌点单」

服务员把菜单、摆盘要求、桌号装饰、口味备注全写在一张大单上递给后厨。 后厨既要炒菜，又要按摆盘图装盘。好处是一趟搞定；坏处是大单越写越厚， 换一种盘子（换图表库）或单独打包外卖（导出/OpenAPI），都得扛整张大单。

我们像「菜品单 + 出餐口」

菜品单（encode）只写：用什么食材、怎么切（维度/指标）。 出餐口（datasetQuery）只负责按标准做菜出一份「通用菜」（标准表）。 前厅再决定装圆盘还是方盘（ECharts / 表格 / 导出）。 多一趟传菜，但厨房规则统一、换盘子不影响炒菜。

2.1 为什么很多开源 BI 选 DataEase 类似协议？

真实原因说明
产品从「做图」长出来 核心用户故事是「拖字段出图」，自然形成「视图对象 = 一切」；getData 是最短路径。
前端驱动迭代快 改完轴配置直接 getData(clone(view))，前后端不用先对齐两套模型。
和渲染库绑死划算 选定 AntV/S2 后，后端直接吐它们爱吃的结构，少一层转换。
团队与仓库一体 开源单体里「图表团队 = 数据团队」，上帝对象的长期成本被短期交付盖住。
所以：不是 DataEase「错了」，而是它优化的是单体 BI 快速出图。 我们若目标是可开源、可换引擎、数据集可复用、权限可审计，继续抄一体 getData，后面拆不动。

2.2 我们到底要解决什么痛？（对照一张表）

痛点DataEase 一体协议我们拆开之后
换前端图表库 后端出参常贴 AntV/S2，换库要改 Handler 库只吃标准表；可选 view 当适配器
非图表也要取数 导出/嵌入也要假装「有一张图」 直接走 datasetQuery，不背图表配置
权限与 SQL 散落 各图 Handler 里各写一段 SQL/RLS/限流只在 datasetQuery 一处
请求体失控 前端多传字段就可能改变查询语义 运行时只传 chartId + 看板上下文；配置另存
协议版本化 上帝 DTO 难演进 保存协议 / 查询协议 / 结果协议可分开升版

2.3 三个词到底是什么？（encode / QuerySpec / 标准表）

用「销售周报 · 区域柱状图」贯穿。先忘掉英文名，看三层纸条。

① encode · 给人看的绑图意图

存在图表配置里。分析师拖字段时改的就是它。不写 SQL，不含筛选现场值。

{
  "category": "region",   // X：按区域
  "value": "amount",      // Y：销售额
  "agg": "SUM"            // 求和
}

人话：「这张柱状图，用区域做类目、金额求和。」

② QuerySpec · 给数仓看的取数单

由后端把 encode + 看板筛选编译出来。仍然不是 SQL，但不含「柱状图/颜色」。

{
  "datasetId": "ds_sales",
  "dimensions": [{ "field": "region" }],
  "measures": [{
    "field": "amount", "agg": "SUM"
  }],
  "filters": {
    "op": "eq", "field": "region",
    "value": "华东"   // 来自切片器
  }
}

人话：「在销售数据集上，按区域汇总金额，且只要华东。」

③ 标准表 · 通用结果

任何引擎都能吃的行列。前端再决定画柱还是出 CSV。

columns: region | amount
rows:
  华东 | 350
  华北 | 205
  华南 | 311

人话：「先给你一张表；怎么画是后话。」

三者关系（一条线）

人改 encode→ 存库→ 运行时编译成 QuerySpec→ datasetQuery 出标准表→ 前端画图

DataEase 把 ①②③ 和「怎么画」揉进同一次 getData 的大 JSON。 我们坚持：① 配置期保存；②③ 运行期算出；画法可换。

2.4 职责到底差在哪？（前端 / 后端）

工作项DataEase 谁做我们谁做差别一句话
记住「图绑了哪些字段」 前端塞进大 DTO，后端也能从 DTO 读 前端改 encode → 后端存 charts 表 我们把「配置」从「取数请求」里拆出去
拼本次筛选/联动 前端写进 chartExtRequest，随大 DTO 提交 前端只传瘦 context；后端编译 Filter 我们禁止前端夹带 SQL/随意条件形状
生成 SQL / 查库 图表 Handler + Provider 仅 datasetQuery + 连接器 图表模块不准直连库
变成柱状图数据结构 后端按 AntV 形状吐出 可选 shape；或前端吃标准表自转 渲染库可替换
数据集预览（无图） 另一套或仍偏视图思维 直接 datasetQuery 出数能力不依赖「有没有图」

2.5 运行期流程（看清「多出来的那一层」干什么）

顶栏可切换协议视图。图可点击放大。

DataEase：一次请求扛全部

前端责任重：必须能组装「完整视图 + 现场筛选」。 后端责任杂：既当配置解释器，又当 SQL 引擎，又当 AntV 适配器。

点击放大
flowchart TB A[前端: 深拷贝整张图的配置] --> B[前端: 塞入筛选联动下钻] B --> C[POST getData 大 JSON] C --> D[后端图表 Handler] D --> E[在 Handler 里拼 SQL] E --> F[查库] F --> G[转成 AntV/S2 结构] G --> H[前端原样渲染]
我们：多一步「编译」，换来边界清晰

前端变瘦：只报 chartId + 现场 context。 多出来的 chartQuery = 翻译官（encode→QuerySpec，不查库）。 datasetQuery = 唯一厨房（查库、权限、限流）。

点击放大
flowchart TB A[前端: 只传 chartId + 筛选上下文] --> B[chartQuery 翻译官] B --> C[读出已存 encode] C --> D[编译成 QuerySpec] D --> E[datasetQuery 唯一厨房] E --> F[权限 + SQL + 查库] F --> G[标准表] G --> H[可选: 转成 ECharts view] H --> I[前端渲染]

配置期 vs 运行期（避免再混）

配置期（改字段、保存）
  • DE：改大 DTO ↔ 保存 ↔ 常立刻 getData
  • 我们：PUT encode 与 chartQuery 分开；保存不等于查库
运行期（筛选、联动、观看）
  • DE：每张图再丢一次大 DTO
  • 我们：每张图一次瘦 query；厨房始终 datasetQuery
决策一句话： 开源 BI 选一体协议，是为了快；我们选拆开，是为了边界干净、能换引擎、数据集可复用、权限可收口。 代价是多一个「翻译官」chartQuery——它不重复查库，只把人看懂的 encode 译成库看懂的 QuerySpec。

3. 真实案例：前端负责什么，后端负责什么

点选案例。每个案例拆成 DataEase / Open Dashboard 两侧的 前端 后端 职责。

案例 A：销售周报 · 柱状图维度从「区域」改为「产品」

用户在数据面板把类目槽换成 product，图表应立刻重绘。

DataEase

前端

  • 改 view.xAxis 字段对象
  • 深拷贝整份 view
  • 附带当前 chartExtRequest
  • 调用 getData；用返回 DTO 调 AntV/S2 render
  • 可能触发画布快照保存

后端

  • 接收完整 ChartViewDTO
  • Handler 读 xAxis/yAxis 编 SQL
  • 走直连或抽取引擎执行
  • ChartDataBuild 转 AntV 结构
  • 把 data 写回同一 DTO 返回
// DE 请求体（语义压缩）
POST /chartData/getData
{ id, tableId, type:"bar",
  xAxis:[{dataeaseName:"product", ...}],
  yAxis:[{dataeaseName:"amount", summary:"sum", ...}],
  chartExtRequest:{ filter:[], ... },
  customAttr, customStyle, senior, ... }
Open Dashboard

前端

  • 只改 encode.category = "product"
  • PUT .../charts/{id} 持久化（可防抖）
  • POST chartQuery 只带 chartId + context
  • 用 result.view 或自转 table→ECharts
  • 不传 style / 不传完整组件树

后端

  • 按 chartId 读已存 encode
  • 编译 dims=[product], measure=SUM(amount)
  • 合并 RLS + context.filters
  • DatasetQuery → 连接器执行
  • 返回 table + 可选 echarts view
// OD 请求体
POST /chartQuery/query
{ "dashboardId":"dash_sales", "chartId":"c_bar",
  "view":"draft",
  "context":{ "filters":[], "linkages":[] } }

// 服务端加载到的 encode（不在请求里重复整树）
{ "category":"product", "value":"amount", "agg":"SUM" }

案例 B：切片器选「华东」· 全页多图刷新

看板顶部区域切片 / 查询控件变更，所有绑定该字段的图重查。

DataEase

前端

  • 维护看板查询组件状态（VQuery）
  • 为每一张图拼 chartExtRequest.filter
  • 每张图各自 getData(整图+ext)
  • 处理加载态 / 错误态

后端

  • 从 extRequest 解析过滤条件
  • 与视图自身 filter 合并
  • 有动态过滤时通常绕过视图缓存
  • 逐图 SQL 执行并塑形
Open Dashboard

前端

  • 更新统一 filterState
  • 对可见 chartId 列表并发 chartQuery
  • 每请求只多带同一 context.filters
  • 不把过滤条件写进 encode 配置

后端

  • context.filters → FilterAST
  • 与数据集 RLS and 合并
  • 按各图 encode 分别编译 QuerySpec
  • 限流 / maxRows；返回标准表
context.filters = [
  { "componentId":"slicer_region", "field":"region",
    "operator":"eq", "value":"华东" }
]

案例 C：点击柱「华北」· 联动明细表

DataEase

前端

  • 监听图点击，查联动配置
  • 把源字段值写入目标图的 extRequest
  • 对目标图再 getData（仍带整图配置）

后端

  • 联动规则服务（配置期）
  • 运行时主要信任前端拼好的过滤
  • Handler 把过滤编进 SQL
Open Dashboard

前端

  • 点击后构造 linkages 项
  • 只对 targetChartId 发 chartQuery
  • 源图无需重传 encode

后端

  • 校验 linkage 是否命中当前 chartId
  • operator/value → FilterAST（禁 SQL）
  • 与看板 filters、RLS 合并后查询
context.linkages = [{
  "sourceChartId":"c_bar", "sourceField":"region", "value":"华北",
  "targetChartId":"c_detail", "targetField":"region"
}]

案例 D：透视表 · 行=区域 × 列=产品 × 指标=金额/销量

DataEase

前端

  • 配置透视轴字段进 view
  • getData 后主要交给 S2 渲染
  • 分页/展开等塞进 extRequest

后端

  • TablePivotHandler 特殊 SQL/聚合
  • 输出贴近 S2 的数据结构
  • 导出 Excel 常复用同一算子
Open Dashboard

前端

  • encode: category/colDim/value[]
  • 请求 shape=table 或默认 view.pivot
  • 可用自研表或日后换 S2，只换渲染

后端

  • QuerySpec: dims=[region,product], measures
  • 先出长表 ResultTable
  • shapeForChart → matrix / 或让前端透视
encode = {
  "category":"region", "colDim":"product",
  "value":["amount","qty"], "agg":"SUM"
}

案例 E：外部分享链接 · 只读观看已发布版

DataEase

前端

  • 分享页加载 panel 快照
  • 每图仍走 getData（带 panel 权限上下文）

后端

  • 分享/面板级鉴权
  • 按视图配置算数（逻辑同编辑态）
  • 权限模型与面板资源绑定深
Open Dashboard

前端

  • token 打开；拉 published 布局
  • chartQuery 统一 view=published
  • 无草稿 encode；无编辑 API

后端

  • token → 只读主体
  • 强制 published 副本
  • 看板 ACL 后仍过数据集 RLS/CLS
  • 与编辑态同一 QuerySpec 管道

4. 协议字段与样例（定稿草案）

DataEase 传输特征 
请求 ≈ 完整视图配置
+ chartExtRequest(运行时)
响应 ≈ 同一视图 + data/fields

前端必须会「组装上帝对象」

Open Dashboard 定稿草案 
// 运行时请求
POST /chartQuery/query
{
  dashboardId, chartId?, view: "draft"|"published",
  inline?: { datasetId, chartType, encode },  // 未保存预览
  context: { filters:[], linkages:[], drill?:[] },
  shape?: "table"|"echarts"|"antv"|"s2"|"raw"   // 默认 table+echarts
}

// 运行时响应
{
  chartId, chartType,
  table: { columns:[], rows:[][], truncated },
  view?: { categories, series } | { kpi } | { pivot },
  meta?: { elapsedMs, sql? }
}

// 底层（仅服务端内聚或内部服务）
POST /datasetQuery/execute  →  QuerySpec  →  ResultTable

5. 多渲染引擎：现在这套能不能换？

能。绑定点只应出现在可选 shape，而不是 encode 存储。

flowchart LR encode[encode 意图] --> spec[QuerySpec] spec --> table[ResultTable 标准表] table --> t[shape=table] table --> e[shape=echarts] table --> a[shape=antv] table --> s[shape=s2] table --> r[shape=raw] e --> ECharts a --> AntVG2 s --> S2 t --> AnyUI

推荐默认

  • 后端永远返回 table
  • 默认附加 view（echarts）方便现有高保
  • 嵌入/导出/新引擎：shape=table|raw 自行塑形

不要做的事

  • 不要把 AntV 字段名写进 encode
  • 不要让「换 S2」迫使改数据集协议
  • 不要为每个引擎复制一套 SQL Handler

6. 异构数据源：后端怎么支持

图表永远不直连源。异构差异收敛在 DatasetQuery 编译期 + DataSourcePort 连接器。

flowchart TB CQ[chartQuery] --> DQ[datasetQuery] DQ --> LP[LogicalPlan + FilterAST] LP --> D1[MySQL 方言] LP --> D2[PostgreSQL] LP --> D3[ClickHouse / Doris] LP --> D4[引擎表 DuckDB] D4 --> X[Excel/CSV/API 同步落地] D1 --> RT[ResultTable] D2 --> RT D3 --> RT D4 --> RT
源类型策略对协议影响
MySQL / PG / Oracle…LogicalPlan → 方言 SQL → JDBC execute无；仍是 QuerySpec
CK / Doris / StarRocks同左；注意分页/函数差异在编译期无
Excel / CSV导入引擎表再查无
HTTP API同步缓存为引擎表（一期）；小结果可受限直查无
不支持的聚合编译期报错或改写错误码进 meta，不改请求形状

连接器接口（稳定面）

interface DataSourcePort {
  ping(cfg)
  listSchemas / listTables / listColumns
  execute(cfg, PhysicalPlan) → ResultTable
}
// PhysicalPlan: { dialect, sql, params, timeoutMs, maxRows }

7. 定稿清单与反例

写入 OpenAPI / 实现时打勾

  • □ 运行时仅 /chartQuery/query
  • □ 底层唯一 /datasetQuery/execute
  • □ 响应必有 table
  • □ 可选 shape / view
  • □ context.filters / linkages / drill → FilterAST
  • □ style 永不进 SQL
  • □ 分享与编辑同一管道，仅 view/鉴权不同

反例（明确禁止）

  • 整份 ChartView 当查询请求
  • 图表 Handler 直连 JDBC
  • 前端传原始 SQL / 任意 datasourceId
  • Map<field,value> 当主结果协议
  • 查全量再内存做行权限
  • 为 AntV/S2 各养一套取数 API
和 hi-fi 的关系： 现在浏览器内 aggregateSeries 只是占位；接后端时每个 paintChart 替换为一次 chartQuery。协议按本文定稿即可持续演进。 详细基线仍见 data-query-architecture.md。
