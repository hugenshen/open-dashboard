1. 目录一览

路径用途
product/overview.md产品是什么
product/requirements.md仅已交付需求基线
product/roadmap.md下一步；按 v0.x 分组并链到提案
design/现行说明书 + openapi.yaml（硬契约）
proposals/进行中 / 已交付规格（用 status 标记）
process.md协作规范正文
prototypes/hi-fi/当前高保原型（可改）
prototypes/snapshots/可选冻结快照（只读）
没有 archive 目录。历史看 proposals 里 status: done，或 git tag（例如 v0.4.0）。

2. 新需求怎么协作

  1. 立项 — 在 roadmap.md 对应里程碑下挂一条，链到即将创建的 Pxxx。
  2. 写规格 — 新建 proposals/Pxxx-*.md：draft → 评审 accepted → 开工 in-progress。
  3. 定契约 — 跨前后端时，先改 design/openapi.yaml 与相关 design 文，再改实现。
  4. 原型（可选） — 有新交互则改 prototypes/hi-fi/；大改前可拷到 snapshots。
  5. 实现 — 前端 / 后端按 OpenAPI 与提案实现；PR 注明 Pxxx。未验收不要写进 requirements。
  6. 交付 — 验收点合并进 requirements.md；roadmap 勾掉；提案改为 status: done 并填 done 日期。
roadmap → proposals/Pxxx → design + openapi → FE/BE → requirements → Pxxx done

短路径（不必走完全程）

类型做法
纯 UI、契约不变可不建提案；必要时补一句 design
文档与线上不符无提案；改 openapi 或改代码
笔误直接改对应文件

3. 版本（里程碑）怎么用

版本用于排期与发版对齐，不是复制多份需求基线。

  • roadmap.md 用 ## v0.5 等分组计划项
  • 提案文首写 milestone: v0.5
  • 发版时 docs / 前端 / 后端尽量打同号 tag（如 v0.5.0）
  • requirements.md 始终只有一份：当前已交付全集；顶部可注明「基线对齐 v0.x」
不要维护长期并存的 requirements-v0.4.md / requirements-v0.5.md 当日常入口。看旧版用 git：git show v0.4.0:docs/product/requirements.md。

4. 场景实例

跨端新功能（如分享加密码）

roadmap 挂条 → 新建提案 in-progress → 改 openapi + design → 前后端实现 → 写入 requirements → 提案标 done。

纯前端（如画布吸附）

可无提案；只改前端（可选补 design/frontend）。

进行中大功能（对话分析 P004）

以 P004 + design/conversation.md + 原型为准；未验收前 requirements 不写「已支持对话分析」。

5. 硬规则

  • 现行契约 = requirements + design（含 OpenAPI）；仅非 done 的提案指导开发。
  • done 提案只读追溯，不驱动新开发。
  • 跨 FE/BE：先合文档契约，再合实现。
  • OpenAPI 与实现冲突：以已上线行为为准，并尽快修契约。
