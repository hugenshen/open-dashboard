1. 背景与问题

P011 把对话迁到 opendashboard-dsh-harness（dsh）后，出板收成 od_generate_board one-shot：稳定、不易超时，但内容质量闸没有跟着迁全。 实跑常见「能出板、不好读」。

典型症状（产品实跑）

现象用户感受根因归类
「支付状态 · 商户费率」柱图 维和度量放一起不知道在讲什么 规划 = 第一个度量 × 第一个维度；无分析目标、无 measureKind
图例显示 MchIncome 字段名用户看不懂 直播查询系列名用原始字段名；未写 alias
金额显示上千亿级「分」 单位不友好 生成带了 formatter，渲染未统一吃；缺数量级
半行空白、下方又有图 板面碎、不清晰 两列布局奇数行未拉满；偶发重复写入
两条查询条件 / 整板复制 像生成了两次 Agent 多次写板 + replace 未先清空
轴上 -1 / 0 / 2 / 3 状态码不可读 枚举未走 glossary / distinct 文案（属 P010）
关键决策（用户确认） 禁止「禁费率」类个案补丁；废弃「板型槽位填充」主叙事。 改造方案集成三层： A 语义（measureKind）→ B 治理（P010）→ C 先 Goal 再出图（LIDA 形）。 详见 §3。

3. 改造方案 · 三大核心流程（明确定义）

业界能稳定出经营看板的产品，几乎都不是「LLM + 裸 schema 直接拼图」。 OD 的改造方案显式集成下面三层；每一层有独立契约、落点与边界，合起来才是完整出板质量路径。

集成原则（2026-08-22 修订） A/B/C 是能力分层，不是必须保留的自研 API 名。 业界开源好用的模块可以直接照搬/改编进仓（prompt、数据结构、枚举→图、agg 契约、自修复规则）； 仍禁止：无适配整仓替换（第二套 Cube 查询面、LIDA 出 matplotlib 再转板、Python harness 复活当主路径）。 落地必须接到现有：Java BI / od_* / DashboardPatch / 编辑器 encode。

LAYER A · SEMANTIC

语义层 · 度量契约

对标：Cube · WrenAI MDL · Cortex · 本仓 /dimensions 指标

业界做什么
度量预定义 type = sum | avg | count；Agent 选指标名，不现场发明口径。
可照搬
度量元数据形状（name / field / agg / unit）；Wren/Cube YAML 里 measure 条目的字段集；SQLBot/Joy 对「指标名→字段+agg」的注入格式。
OD 落点
优先接通已有 de_indicator（知识维护已确认的 agg），再启发式补洞；出板读 confirmed metrics，不只读 schema。
不整仓
不部署独立 Cube/Wren 查询服务当出板引擎；公式/join 语义平台本期不做。

LAYER B · GOVERNANCE

治理后再问 · 字段与枚举原则

对标：JoyDataAgent DGP · TableRAG · SQLBot dimension-values · 本仓 /dimensions

业界做什么
先治理表/字段/枚举，再问数；脏码值不直接上轴。
可照搬
SQLBot <dimension-values> / 术语注入块；Joy TableRAG「选表选字段」的裁剪与打分思路（改编进 schema 加厚，不搬整套 RAG 服务）。
OD 落点
P010 glossary + 枚举值；出板/问数只读 confirmed；轴文案与 kind 回写走管理面。
不整仓
不把 Joy 整仓 data_agent 当对话运行时；治理 UI 继续收敛在知识维护，不另起平台。

LAYER C · AUTO-VIZ

自动可视化 · Goal → Chart

对标：Microsoft LIDA（Summarizer / GoalExplorer / VizGenerator / critique）

业界做什么
summary → 枚举 goal(question, visualization, rationale) → 为每个 goal 生成图 → 自评估/修复。
可照搬
LIDA 的管线与 JSON 目标结构（question / title / rationale）；Goal 提示词骨架；critique 维度清单。Viz 输出改写成 OD encode，不要 matplotlib 代码。
OD 落点
od_plan_charts 展示 goals；生成可走「确定性模板」或「LLM GoalExplorer + 确定性 review 闸」双模，闸门不可跳过。
不整仓
不把 LIDA Python 包当主进程；不恢复已删的 Python harness 出板主路径；Infographer/IGM 不做。

13.1 开源 / 业界问数怎么跑评测

产品型 ChatBI（SQLBot、Joy）很少把公开榜当主验收；论文/Agent 框架才追 Spider / BIRD 榜。 但评测方法论高度一致，OD 应对齐「怎么判对」，而不是盲目刷榜。

层级代表输入怎么判「对」谁在用
学术公开榜 Spider 1.0 · BIRD · Spider 2.0 题面 + DB schema（BIRD 还有 external knowledge 提示） 主指标 Execution Accuracy (EX)：生成 SQL 与 gold SQL 在同一库执行，结果集等价（优于字符串 Exact Match）。BIRD 另有效率分 VES；Spider 2.0 看多步工作流成功率 论文、Text2SQL Agent、部分 ChatBI 宣发
跑法（公开集） 官方 eval 脚本 / Spider-Agent 类 harness dev/test jsonl ① 系统出 SQL → ② 在 SQLite/Snowflake/BQ 执行 → ③ 与 gold 结果比对 → ④ 汇总 EX% 开源 Agent 复现榜
产品 ChatBI SQLBot · Joy DataAgent · Vanna 自有业务表 + 训练对 / 术语 人工抽检 + 业务金标（NL→正确结果）；训练对回归；很少公开 Spider 分数当质量门 交付产品
语义层产品 Cube · Wren MDL / Cube measure 指标编译正确、agg 不漂；不是 NL→任意 SQL 榜 指标治理 
# 业界主流判分（问数）
gold:  (question, db, sql*)     * 或等价结果指纹
pred:  system(question, schema[, knowledge]) → sql
score: EX = exec(pred) ≡ exec(gold)   ← 对齐这个，不要对齐「SQL 字符串长得像」

# 公开集在测什么（映射到 OD 缺口）
Spider     跨域 schema 复杂度、嵌套 SQL
BIRD       脏值/库内容、外部知识（≈ 我们的 terms/维值）
Spider 2.0 企业超宽表、多方言、多步 Agent
产品金标   专有指标口径、权限、业务黑话（公开集覆盖最弱）
