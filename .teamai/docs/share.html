1. 这份介绍给谁

不是终端用户手册（那是 user-manual）。本页回答四件事：

  1. 开源产品 DataQ / Open Dashboard 给谁用；
  2. 协同框架 TeamAI 解决什么，官方怎么用；
  3. 本仓 Co-TeamAI 怎样把官方 harness 接到产品契约上；
  4. 一个真实缺口（出板确认后对话卡太粗）各角色该改哪些文件。
聊天里确认的范围，当轮必须写进 Pxxx。下一棒只认提案和 acceptance.yaml，不认聊天记录。

2. 两种「用户」

产品用户（DataQ）

用软件的人。写在 product/README.md。

角色典型场景
分析师接数、建数据集、对话出板、发布看板
业务读者打开分享链接只读观看
报告作者写正文、插入看板图或报告内新建图
接入方用企业身份接入，不强制自带登录页

协同角色（做这个产品的人）

改契约和代码的人。写在 process.md 与 manifest/roles.yaml。

Role覆盖
ba需求 + 高保。产品语言，不写技术方案
dev方案设计 + 实现
test按 yaml 验收，只改 status / evidence

AI 不是第五工种，是当前角色的搭档。

3. TeamAI 是什么

TeamAI（命令 teamai）是面向 AI 智能体的团队 Harness：用 Git 统一管理 skills、rules、docs、hooks、mcp、经验，再注入 Cursor / Claude Code / Codex 等工具。官方中文说明见 README.zh-CN.md。

官方默认路径是：先有一个共享经验仓库（Team Repo），成员在各自业务仓里 teamai init <Team Repo URL>，会话开始自动 teamai pull。

teamai push  →  分支 + MR  →  合并
                    ↓
SessionStart hook  →  teamai pull  →  同步到本机 AI 工具

官方还提供：角色（只同步匹配的 skills）、标签、订阅源、知识召回、用量周报。起步模板之一是 teamai-hub/template-backend：按上游来源分命名空间（skills/ecc/ 后端模式、skills/mattpocock/ 工程方法），全员 rules/common/，以及评审子代理。

模板解决的是「后端工程师通用装备从哪来」。它不是本产品的需求/验收真相。本仓如果要用 ecc / mattpocock，按命名空间拷进 .teamai/skills/ 或 teamai source add，不要再 init 第二个 Team Repo。

4. 本仓怎么落地

对外品牌 Co-TeamAI。目录和命令仍是官方约定的 .teamai/ / teamai。开源仓本身就是 Team Repo（mode: self），知识跟着 clone 走，不另立门户。

官方概念本仓落点
Team Repo本仓库 open-dashboard，不是第二份仓
docs 知识库.teamai/docs/（唯一契约树；仓库根没有 docs/，没有符号链接）
skills / rules.teamai/skills/ · .teamai/rules/，与 process 同一套，不另写真相
角色分发.teamai/manifest/roles.yaml：ba / dev / test
skills 命名空间按交接角色：common/ · ba/ · dev/ · test/（不是按上游 ecc / mattpocock）
culture.teamai/culture.md，teamai pull 时注入
recallteamai.yaml 已开 sharing.recall.enabled

只跑产品、不协同的人：./scripts/up.sh，不必装 teamai。

本仓 skills（按角色裁剪）

命名空间技能何时用
commonod-rd-loop · od-local-verify先对齐再写代码；真实路径验证
baod-write-proposal · od-hi-fi写 Pxxx 范围与 criterion；改 hi-fi
devod-solution-design · od-implement-proposal先 design / OpenAPI，再按开发入口实现
testod-acceptance只改 yaml 的 status / evidence

全员仍能看见整棵 docs 和根目录 rules。Role 只裁剪 skills，不裁剪产品真相。

5. 角色：五棒交接 × 三个 Role

人按棒交接，skill 只分三个工种。BA 不懂技术细节时，方案设计归开发。

@需求(BA)→ @高保(BA)→ @方案设计(开发)→ @实现(开发)→ @测试

棒谁先打开产出不要做
需求 BA roadmap · 提案 README 范围 / 非目标 / yaml criterion 写 design.md、OpenAPI、类名
高保 BA hi-fi / VERSIONS 交互可对照；定稿打 snapshot 改冻结 snapshots；用高保代替方案
方案设计 开发 提案 design/ · OpenAPI 怎么做、契约草案、代码落点 改 criterion；未写方案就改产品代码
实现 开发 README「开发入口」 FE / BE / dsh；architecture 同提交 从聊天或最新 hi-fi 猜范围
测试 测试 test/acceptance.yaml status / evidence 改判据；「代码已合」当验收

gates.hi-fi=none 时可跳过高保；改模块边界或跨端时不能跳过方案设计。同一人可兼角（teamai roles set ba --add dev），但不能跳棒。

6. 规范核心：真相分层

Pxxx 是需求、高保、方案、实现、验收的主键。目录不搬家，进度看 roadmap/<状态>/ 和文首 status / gates。

路径只存什么
product/README.md产品是什么、给谁、模块边界
product/roadmap/Now / Shipped / Later / Won’t；当前开发只看 in-progress
proposals/Pxxx-name/未交付：README 地图 + req/ · design/ · test/
prototypes/hi-fi 可改；snapshots 冻结
design/architecture.html已实现 4A，只写代码里能证实的事实
design/openapi.yamlFE↔BE 硬契约
product/requirements.md已验收能力基线

四个 gate 不能互相替代：proposal / hi-fi / code / acceptance。现行契约 = requirements + architecture + OpenAPI；未来设计只留在未 done 的提案里。

roadmap 挂条
  → 提案（需求 + 设计 + 验收 + 开发入口）
  → 高保（需要时；定稿打 snapshot）
  → OpenAPI（跨端）→ 实现
  → architecture 同提交
  → yaml pass → 回写 requirements → 挪到 done/

7. 别人怎么加入

只跑产品

./scripts/up.sh
# Web http://127.0.0.1:8088

要和人 / AI 一起改需求或代码

  1. 安装 CLI：npm install -g teamai-cli（见 官方 README）。
  2. clone 本仓，在仓库根执行 teamai init .（单仓，不是再 init 一个模板仓）。首次可能写 AI settings，看一眼 git status。
  3. 认身份：teamai roles set ba 或 dev / test。兼角加 --add。然后 teamai pull。
  4. 看 in-progress：不在这页的条目不要当当前任务。
  5. 打开对应提案 README 的「开发入口」。实现对照入口表，不要对照最新 hi-fi（已冻结则对照 snapshot）。
  6. docs / hooks / mcp 用普通 git commit。skills / rules 也可用 teamai push 走评审。
不要对 .teamai/docs/ 跑 teamai uninstall 的 docs 清理。不要符号链接。不要在仓库根再建一份 docs/。

8. 实例：确认后对话看不到图怎么配

产品现象：分析师在对话里确认「订单经营仪表盘」规划后，左栏只剩「Draft 已导入 + 打开编辑器」，右侧能看见板，但看不到每张图怎么生成、数据配置、中间过程。

协同判断（先走 od-rd-loop）：这是出板结果卡，属于进行中的 P015，不是 P016 分析报告，不要新建 P017。

棒本案例实际做了什么改哪些文件
需求 BA 锁：确认后左栏必须能看进度、每图配置、可展开详情；右侧预览不能当唯一真相 P015 README 范围 / 差距；yaml criterion（PR-REAL-23）
高保 BA hi-fi: none，不新开原型页，交互写在 design 文案卡 不改 snapshots
方案 开发 board_ready 带 charts[]；对话卡展开详情；不改 OpenAPI（harness 展示元数据） design.md §11.4；yaml command_or_path
实现 开发 下一棒：按开发入口改 harness 对话卡 answer-meta.js · BoardPreviewView 等（尚未开工）
测试 代码合入后手验：不打开右侧也能在对话里核对每图口径 只改 acceptance.yaml 的 status / evidence

这就是「规范在干活」：缺口从截图变成可交接的 ID；下一棒有入口；AI 跟当前角色走，不会既改判据又改代码。

9. 不要做

  • 把未验收能力写进 requirements.md 或现行 4A。
  • 从聊天或最新 hi-fi 猜测实现范围；hi-fi: accepted 必须对照 snapshot。
  • BA 写模块 / 接口 / 数据流；测试改 criterion。
  • 已在 in-progress 的缺口另开一个 Pxxx「好看一点」。
  • 用 mattpocock / ecc 技能另立 spec、ADR 树或一次性高保世界。
  • 把 worker 细工具名、原始结果行、prompt 贴进对话（P015 明确非目标）。
