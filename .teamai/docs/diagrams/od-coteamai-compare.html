1. 图在讲什么

上半：传统 AI Agent

主张：把协同做成可编程智能体，就要配齐管道。

  1. 配置文件 CLAUDE.md（目标 + 工具权限）
  2. 智能体定义 Agents.md（Researcher / Writer）
  3. 模型选择（GPT-4o、Claude、Gemini、Llama…）
  4. I/O 路由与编排（用户输入 / 文件 / DB / API / 网页 ↔ LLM / 工具 / 发消息）
  5. 触发条件 A / B / C
  6. 动作定义（参数、模板、通知、字段映射、分支）

右侧圆柱：上下文、变量、历史、任务队列。状态在「系统里」，不在契约树里。

下半：Co-TeamAI

主张：不要配一窝 Agent，@ 当前角色即可。

需求(BA)→ 高保(BA)→ 方案设计(开发)→ 实现(开发)→ 测试

  • 人发起，用 @ 交接
  • 角色是研发棒次，不是 Researcher / Writer
  • 没有画出 Pxxx、gate、docs、skills
这张图回答的是「和传统 Agent 编排比，我们换了一种形状」。本仓真正落地的是另一句话：人与 AI 走同一条角色链，真相在 .teamai/docs/，AI 不是第五工种。

4. 六步对照表

process.md 有一张「AI 工作流（对应图上半）」——那是仓库想让上半表达的映射。当前图上半画的是左边；仓库跑的是右边。

步图上半实际画的本仓真实落点
1 配置 CLAUDE.md 目标 + 工具权限 AGENTS.md · process.md · .teamai/rules/（可读 docs、可写提案与代码、禁改 snapshots）
2 角色 / 智能体 Researcher / Writer 两个 Agent 交接五棒；skill 只分 ba / dev / test
3 模型 表盘锁 Claude 3.5 Sonnet 等 不锁模型
4 I/O 通用 LLM/工具/网页意大利面 输入：@、roadmap、Pxxx、hi-fi、OpenAPI、代码；输出：回写提案、快照、契约、PR、4A、yaml
5 触发 条件 A? B? C? in-progress/ · 对应 gate · 人确认
6 动作 工具参数、模板、通知渠道、字段映射、分支逻辑 写 Pxxx、打快照、改 OpenAPI、改代码、改 yaml status；pass 才写 requirements
状态 上下文 / 变量 / 历史 / 任务队列 上下文=当前 Pxxx；变量=gates；历史=snapshots 与 git tag

5. 本仓 AI Native 框架实际长什么样

转型引入的不是「五个头像流水线」，而是一套跟 clone 走的团队 Harness：官方 TeamAI CLI（mode: self）+ 本仓契约树。对外品牌 Co-TeamAI，目录仍是 .teamai/。

.teamai/
├── teamai.yaml          # 单仓、recall、强制规则
├── culture.md           # pull 时注入
├── manifest/roles.yaml  # ba / dev / test
├── rules/               # 短规则，与 process 同一套真相
│     od-docs-truth · od-roles · od-dev-entry · od-hi-fi · od-delivery
├── skills/              # 按角色裁剪，不另写真相
│     common/  od-rd-loop · od-local-verify
│     ba/      od-write-proposal · od-hi-fi
│     dev/     od-solution-design · od-implement-proposal
│     test/    od-acceptance
├── learnings/           # 0→1 踩坑（聊天不是真相、先对齐再代码…）
└── docs/                # 唯一产品/工程契约
      product/  roadmap · requirements
      proposals/Pxxx-name/  req/ · design/ · test/
      design/   architecture.html · openapi.yaml
      prototypes/  hi-fi/ · snapshots/
主键
Pxxx。提案目录不搬家；进度看 roadmap/<状态>/ 和文首 status / gates。
真相分层
未交付只在提案；4A 只写已实现；requirements.md 只写已验收。聊天确认的边界当轮回写 Pxxx。
四个 gate
proposal / hi-fi / code / acceptance 不能互相替代。高保通过或代码存在，都不能当产品验收。
Role × 棒
人按五棒交接；skill 只分三个工种。同一人可兼角，不能跳棒（高保可按 gate 省略）。
开发入口
实现只打开 in-progress 提案 README 的「开发入口」。已 hi-fi: accepted 对照 snapshot，不对照最新 hi-fi。
交付顺序
OpenAPI → 实现与验证 → architecture 同提交 → yaml pass → 回写 requirements → 挪到 done/。

人怎么开工（仓里真实触发，不是图上的条件 A/B/C）

  1. clone 后仓库根 teamai init .，teamai roles set ba|dev|test，teamai pull。
  2. 只看 roadmap/in-progress。
  3. 打开对应 Pxxx README「开发入口」。
  4. 按当前 Role 走 skill：先 od-rd-loop 分类，未对齐不改产品代码。
  5. 测试只改 acceptance.yaml 的 status / evidence。

6. 图没画出、仓里真正起作用的东西

这些才是「往 AI Native 转」时引入的骨架。图为了对照传统 Agent，把它们全省略了：

仓里的机制干什么图上有没有
Pxxx 主键 + 开发入口下一棒只认提案，不认聊天无
文档真相分层未实现不进 4A，未验收不进 requirements无
四层 gate高保 / 代码 / 产品验收分开记无
3 Role × 5 棒skill 裁剪，不是五个独立 Agent只画了五棒人名
rules 注入每个 IDE 会话自动带短规则无（上半还是 CLAUDE.md）
skills先对齐再实现、按棒写提案/方案/验收无
learnings质量闸不是 prompt、权限 fail-closed、真实路径验证无
hi-fi vs snapshotaccepted 对照冻结版无
OpenAPI 同 PR跨端契约与代码一起合无
AI 跟当前角色BA 会话不写 design.md；测试会话不改 criterion下半把 AI 画没了

7. 以后怎么读这张图

适合用这张图讲的

  • 我们不配 Researcher/Writer 管道
  • 交接是 @角色，不是另开 Agent 编排
  • 五棒名字：BA 两棒，开发两棒，测试一棒

不要用这张图当运行手册

  • 上半不是本仓配置；本仓入口是 AGENTS.md
  • 怎么开工看 guide.html / share.html
  • 当前任务只看 in-progress + 提案开发入口
若要让「图 = 仓」，有两条路，不要混：
A. 保持这张对照海报，改 process.md / share 配文为「上半=传统 Agent，下半=本仓角色链」。
B. 把上半改回本仓六步落点（AGENTS.md、三 Role、不锁模型、docs I/O、in-progress+gate、yaml/PR），下半继续五棒。那才是「人与 AI 同一条链」的结构图。
