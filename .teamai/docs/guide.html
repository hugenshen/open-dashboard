1b. 与 Co-TeamAI 怎么结合

本页所在的树就是 TeamAI 单仓的 docs 资源。探索出来的落地规范（process / Pxxx / 4A / 高保）直接放在 .teamai/docs/，和 rules/、skills/、culture.md 同级，不要符号链接，也不要在仓库根再放一份 docs/。

路径角色
.teamai/docs/产品与工程契约（本树）
.teamai/rules/ · skills/ · learnings/短规则、研发技能、0→1 踩坑；不另写真相
.teamai/culture.mdteamai pull 时注入
.teamai/teamai.yamlsharing.docs.localDir 必须是 ./.teamai/docs

对外品牌 Co-TeamAI；目录与命令仍是 .teamai/ / teamai。clone 后在仓库根执行 teamai init .。docs / hooks / mcp 用普通 git commit。不要对这棵树跑 teamai uninstall 的 docs 清理。

2. 角色链 · 谁读什么

同一套真相，按角色只换入口，不复制文档。聊天记录不是长期真相。协作图：od-coteamai-role-flow.png。

交接：@需求(BA) → @高保(BA) → @方案设计(开发) → @实现(开发) → @测试。方案设计由开发写，BA 不写模块/接口/数据流。

角色目标先打开产出 / 交给谁
规划 & BA（需求） 锁范围与验收 ID product/README.md · roadmap · 提案 README · 可选 req/ 挂条、yaml criterion；不写 提案 design/ → @高保
高保设计 交互可对照 提案 prototype · hi-fi · VERSIONS.md BA：acceptance 快照 → @方案设计（开发）
方案设计 技术怎么做可对照 提案 design/ · openapi.yaml 开发写流程/模型/边界/契约 + 代码落点 → 实现
开发（实现） 按入口改代码 README「开发入口」→ 冻结快照或 hi-fi → OpenAPI FE/BE/dsh + architecture → @测试
测试 判定能否上线 test/acceptance.yaml + prototype-snapshot 只改 status / evidence；pass 才交付
AI 跟当前角色走同一条链 AGENTS.md + .teamai/rules/ 当轮回写 Pxxx；未验收不进 requirements / 4A
提案目录按 Pxxx 主键不搬家。进度看 roadmap/<状态>/ 和文首 status / gates，不要看聊天或最新 hi-fi。 实例：确认后对话看不到图怎么配 → 收进进行中的 P015（PR-REAL-23），不新开号。BA 写判据，开发写方案，实现后再验收。

3. 本仓契约与工程技能包

本仓 .teamai/docs/ 和 mattpocock/skills 不是同一类东西，也不能互相替代。

技能包管怎么干活（Agent 怎么问清楚、写 spec、拆票、TDD）。.teamai/docs/ 管这个产品的事实是什么（做到哪、对照哪份原型、怎么验收）。.teamai/rules/ 与 skills/ 只是把同一套规范注入 AI，不另开第二份契约。

本仓 .teamai/docs/mattpocock/skills
性质 团队知识沉淀与交付契约 Agent 可调用的通用工程工作流
内容 路线图、Pxxx、验收、4A、OpenAPI、高保 /grill-with-docs、/to-spec、/implement、/tdd、一次性 prototype
何时变 随产品和提案变 随工程方法变，与看板业务无关
开发入口 提案 README「开发入口」 你输入的技能命令，例如 /implement

可以对应，但不要两套真相

技能本仓落点注意
/grill-with-docs、CONTEXT.md、ADR 多轮对话回写 Pxxx；术语可进 product/README.md 产品决策写进提案，不要另开一套 ADR 树
/to-spec proposals/Pxxx-name/ 本仓 spec 就是提案，不要再生成一份独立 spec
/to-tickets acceptance.yaml 的可执行项 票是 Pxxx 的切片，主键仍是 Pxxx
技能里的 prototype 一次性 HTML，用来回答一个设计问题 本仓高保是可验收基线（hi-fi + snapshots），不要用 throwaway 流程维护
/implement 先读「开发入口」，再改代码 技能管节奏（TDD、review），不管定义需求
/triage 与 issue 状态 product/roadmap/ 状态夹 进度以路线图为准；GitHub / Linear 只是可选镜像
/setup-matt-pocock-skills 问「文档存在哪」时指向 .teamai/docs/ 不要再造 docs/ai/、specs/、平行 CONTEXT 世界
技能包可以当加速器，挂在 AGENTS.md 的工作方式之外。两套都写「当前该做什么」时，以提案和路线图为准；技能输出只能回写这些文件，不能另立门户。

本仓 skills / learnings（0→1 沉淀）

契约仍只在 docs/。下面这些是 Cursor 从 0 到 1 沉淀的干活方式和踩坑，给下一轮 AI 和协作者用，不另写真相。

路径何时用
skills/od-rd-loop/ 先判断：讨论、高保、写提案、实现、验证，禁止没对齐就改产品代码
skills/od-write-proposal/ 新建或改 Pxxx、开发入口、波及、acceptance.yaml

4. 新需求怎么协作

  1. 立项 — 在 product/roadmap/planned/ 或 in-progress/ 的 README 加一行，链到即将创建的 Pxxx。
  2. 写提案 — 新建 proposals/Pxxx-name/README.md，文首写状态，正文先写「开发入口」，并补 test/acceptance.yaml。
  3. 建映射 — 用 Pxxx 关联增量原型、冻结快照、详细设计、architecture 与 PR-*。
  4. 原型 — 改 hi-fi/；过程打 increment 快照，定稿打 acceptance 快照并写入 prototype-snapshot。
  5. 实现 — 打开该提案「开发入口」。高保已 accepted 时对照快照，不要对照最新 hi-fi。未验收不要写进 requirements。
  6. 架构同步 — 代码验证并提交时，在同一提交更新 design/architecture.html；只写最终架构事实。
  7. 交付 — 已验收能力写入 requirements.md；把该行挪到 roadmap/done/，提案改为 done。
roadmap/状态夹 README 挂条 → proposal 开发入口 → hi-fi 增量 / snapshot 冻结 → OpenAPI → 代码 + architecture → requirements → 该行挪到 done/
开发某个提案时：打开 proposals/Pxxx-name/README.md 顶部的状态行和开发入口表。它会告诉你读 design/ 还是 test/acceptance.yaml、对照 hi-fi 还是冻结快照、改哪些代码。提案目录不随状态搬家。
能力地图、模块边界、数据流、技术栈或部署变化，必须和代码在同一提交更新 architecture.html；类名、函数细节、候选方案留在 Pxxx。
三个 gate 不能混用：高保通过只代表交互基线，代码合入只代表实现存在；仅当 test/acceptance.yaml 的阻塞项全部 pass，才可回写 requirements 并把提案标记为 done。

短路径（不必走完全程）

类型做法
小型纯 UI、契约不变可不建提案；改变长期架构或能力基线时再更新 architecture/requirements
文档与线上不符无提案；改 openapi 或改代码
笔误直接改对应文件

提案里必须能看见波及

每个在途提案 README 用一张表写清影响面，避免把下一轮想法做进当前范围（例如 P007 壳层不要顺便做 P008 权限工作台）。

列写什么
依赖必须先存在的提案或已交付能力
改动面FE / BE / Harness / OpenAPI / 高保，以及明确「不改」什么
回归验收本提案和依赖提案里要复测的 PR-* ID
不要动已拆到其他提案的范围

4.1 高保原型怎么改

高保是文档资产，放在 .teamai/docs/prototypes/。当前增量只改 hi-fi/；历史冻结看 VERSIONS.md 与 snapshots/（只读，看 SNAPSHOT.md 的提案 / kind / 相对上一版）。清单见 MANIFEST.md。预览：.teamai/docs/prototypes/hi-fi/start.sh。

文件改什么
shared/shell.css · shell.js左栏 + 顶栏产品壳（各页统一引用）
workbench.html工作台
conversation.html对话
datasource.html数据源
dataset.html数据集
dashboard.html仪表盘
report.html报告
一模块一页。壳层只改 shared/。高保必须挂提案并更新 MANIFEST。打快照：cd .teamai/docs/prototypes && ./snapshot.sh YYYY-MM-DD-slug "说明" Pxxx increment|acceptance。acceptance 快照才是实现对照版。

5. 验收清单怎么维护

test/acceptance.yaml 是测试与发版共用的那一份清单，不是第二份需求说明书。能维护的前提：判据、路径、状态、证据只写在 yaml 里。

谁动什么何时
BA / 规划相关 ID、标题、criterion锁范围；范围变更时必须改 yaml 并记修订
测试只改 status / evidence高保验收、代码验收、月底放行
开发 / AIcommand_or_path、code gate 的命令实现对照路径变化时
  • README 只保留 ID + 一句话标题，不要复制 criterion / expected / status 长表。
  • 一条在途提案建议 5～12 条阻塞项；当前不做的不要写进 in-progress/。
  • done 之后 yaml 冻结，只追溯。
  • 不要再平行维护 Excel / 禅道测试用例页；缺陷单只贴 PR-SH-10 这类稳定 ID。
yaml 会烂掉的三种情况：和 README 双写、一个提案上百条还跨好几个月、聊天里改了范围却不改清单。

6. 版本怎么分层

有四层，不要合成一层，也不要再加第五套版本文件。

层机制干什么
产品里程碑提案 milestone: v0.x · 状态夹这个大版本要交付哪些 Pxxx
当前进度in-progress/正在做的条目与当前验收 ID
交互VERSIONS.md + snapshotsincrement 是过程档；acceptance 才是实现对照
发版git tag（如 v0.5.0）整仓可回放；含当时的 requirements

requirements.md 始终只有一份：当前已交付全集。不要维护长期并存的 requirements-v0.4.md。看旧版：git show v0.4.0:.teamai/docs/product/requirements.md。

当前动手的只看 in-progress/。P008 可以和 P004 同在进行中，但「当前范围」列写清还没开始高保/代码，开发就不要顺手做。

7. 按状态怎么推进

进度只看状态夹，每夹一份 README。当前开发看 in-progress/。不要按月建文件，也不要为每条再建 Pxxx.md。验收 ID 写在提案 test/acceptance.yaml。

过程产物不要平行繁殖：不要另开「迭代需求说明书」「测试用例.xls」「发版 checklist.doc」。

过程已有产物
排期路线图状态夹
需求 / 边界提案 README（范围、非目标、波及）
交互hi-fi 增量 → 定稿 snapshot
怎么做提案内 design/
契约design/openapi.yaml
是否可上线test/acceptance.yaml 的 status
已上线真相requirements + architecture + git tag
  1. 立项 — 在 planned 或 in-progress 挂条；BA 锁范围；测试确认 ID 可测。
  2. 交互冻结 — 改 hi-fi；测试跑 gate: hi-fi；通过后打 acceptance 快照。
  3. 实现 — 跨端先改 OpenAPI 再改代码；PR 带 Pxxx；边界变化时 architecture.html 同提交。
  4. 验收 — yaml 阻塞项 pass 才回写 requirements。未做完保持 in-progress。
  5. 交付 — 全部阻塞项 pass 后把该行挪到 done/，提案标 done，可打 git tag。

例如 P007 产品门只剩 PR-SH-10：in-progress 表的「当前范围」写这一条；P008 同夹但范围写「尚未开始」，开发就不要动它。PR-SH-10 过了只回写这一条，P007 仍可留在进行中。

8. 提交与发版

  • Commit / PR 标题带 Pxxx，例如 P007: 用 AppShell 替换 ModuleTopbar。
  • 跨端同一 PR：OpenAPI 与实现一起合，契约不单独合入。
  • 模块边界、数据流、技术栈或部署变化：architecture.html 必须同 commit。
  • tag 的内容 = blocker_of_done: true 且 status: pass 的项；未 pass 的不得进 requirements。

9. 场景实例

跨端新功能（如分享加密码）

roadmap 挂条 → 提案目录内写需求与详细设计 → 接受后先契约再实现 → 验证时同提交更新 architecture → 验收后写 requirements → 提案标 done。

纯前端（如画布吸附）

小改可无提案；先实现验收，仅在改变应用边界或长期能力时更新 architecture/requirements。

进行中大功能（对话分析 P004）

先看 进行中 确认仍在该夹，再打开 提案开发入口。实现对照入口表里的原型；验收前 requirements 不写「已支持对话分析」。

部分交付（产品壳 P007）

高保 ID 已 pass 只说明交互冻结。当前范围若只含 PR-SH-10，只回写这一条；P007 保持 in-progress，权限工作台仍走 P008。

10. 硬规则

  • 现行契约 = requirements + architecture + OpenAPI；未来需求与设计只在非 done 提案中指导开发。
  • design/ 只保留 architecture.html、architecture.md（检索索引）与 openapi.yaml；未实现详细设计只进提案目录。
  • Pxxx 是 proposal、prototype、architecture、implementation 与 PR-* 的统一映射主键；目录不随状态搬家。
  • 进度按状态夹；每夹一份 README。当前开发只做 in-progress/ 里写了当前范围的条目。
  • test/acceptance.yaml 是验收状态唯一真相；README 不复制长表。提案根上只留 README，按角色分 req/ · design/ · test/。
  • 高保、代码、产品验收三个 gate 不能互相替代。
  • done 提案只读追溯，不驱动新开发；部分交付时提案保持 in-progress。
  • 跨 FE/BE：先更新 OpenAPI，再改实现；代码验证提交时同步更新 architecture。
  • OpenAPI 与实现冲突：以已上线行为为准，并尽快修契约。
  • 改流转时，必须同时改 AGENTS.md、process.md、.teamai/docs/README.md、本页、proposals/README.md。
  • 工程技能包（如 mattpocock/skills）只加速过程；产出必须回写本仓 .teamai/docs/，禁止平行 spec、ADR 树或 throwaway 高保。
  • 契约只在 .teamai/docs/；不要符号链接，不要在仓库根再建 docs/。
